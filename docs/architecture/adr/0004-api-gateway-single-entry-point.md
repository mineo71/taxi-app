# ADR-0004: API Gateway як єдина точка входу

- **Статус:** Прийнято
- **Дата:** 2026-10-15

## Контекст

Три клієнти звертаються до кількох внутрішніх сервісів. Кожному запиту потрібні однакові речі: перевірка токена, права доступу, обмеження частоти запитів, журналювання ([NFR-11](../../requirements/non-functional.md), [NFR-13](../../requirements/non-functional.md), [NFR-14](../../requirements/non-functional.md)).

Оновлення мобільного застосунку доходить до всіх користувачів тижнями. Якби адреси сервісів були зашиті в застосунку, будь-яка зміна архітектури ламала б старі версії.

## Рішення

Усі клієнти звертаються до системи лише через **API Gateway** (Node.js). Шлюз виконує автентифікацію, перевірку прав, rate limiting і маршрутизацію до внутрішніх сервісів. Назовні відкритий лише шлюз; внутрішні сервіси працюють у приватній мережі.

## Розглянуті альтернативи

- **Прямі виклики сервісів з клієнтів** — клієнт знає внутрішню будову, перевірки дублюються в кожному сервісі, зростає поверхня атаки.
- **Backend for Frontend на кожен клієнт** — надлишково для MVP; можна виділити пізніше на основі шлюзу.

## Наслідки

**Позитивні:**

- Клієнт не знає внутрішньої будови: сьогодні за шлюзом чотири сервіси, завтра вісім, а застосунок на телефоні не змінюється.
- Спільні перевірки реалізовані в одному місці.
- Одна точка захисту від зовнішніх атак.
- Шлюз може зібрати відповідь із кількох сервісів одним запитом — це економить батарею й трафік.

**Негативні:**

- Шлюз — критична точка: потрібні кілька екземплярів за балансувальником ([NFR-7](../../requirements/non-functional.md)).
- Додаткова мережева ланка збільшує затримку — її враховано в бюджеті 300 мс ([NFR-3](../../requirements/non-functional.md)).
