# ADR-0002: Монорепозиторій для клієнтів, сервісів і документації

- **Статус:** Прийнято
- **Дата:** 2026-10-15

## Контекст

Система складається з трьох клієнтських застосунків, шлюзу, сервісу реального часу, чотирьох внутрішніх сервісів і спільних контрактів між ними (тарифи, формати подій, gRPC-схеми). Команда невелика ([CON-3](../../requirements/constraints.md)), а зміна однієї функції часто зачіпає кілька частин одночасно — наприклад, новий статус поїздки змінює сервіс замовлень, обидва мобільні застосунки та адмінку. Вимога [NFR-24](../../requirements/non-functional.md) передбачає модульність і CI/CD.

## Рішення

Увесь код і документація зберігаються в одному репозиторії:

- `apps/` — клієнтські застосунки;
- `services/` — бекенд-сервіси;
- `packages/` — спільний код і контракти;
- `docs/` — вимоги, архітектура, ADR.

## Розглянуті альтернативи

- **Окремий репозиторій на кожен сервіс** — для невеликої команди це зайві накладні витрати: синхронізація версій контрактів, кілька пайплайнів, зміни однієї функції розкидані по різних pull request.

## Наслідки

**Позитивні:**

- Одна зміна функції — один pull request, атомарні зміни контрактів.
- Спільні тарифи й формати подій лежать у `packages/` і не дублюються.
- Документація змінюється разом із кодом.

**Негативні:**

- CI має запускати перевірки лише для змінених частин, інакше збирання сповільнюється.
- Потрібні правила володіння директоріями (CODEOWNERS) у міру зростання команди.
